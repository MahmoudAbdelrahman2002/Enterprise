## 2. High Priority Issues

### QA-001 — [Solved] Checkout fails in both tested stores

**ID:** QA-001  
**Status:** **Solved** — implementation and checkout integration verified 4 October 2026.  
**Resolution:** Historical API logs identified Stripe requests without an API key. Development now inherits the configured test key, and the gateway constructs an explicit Stripe client. Missing configuration or Stripe checkout failures return a localized HTTP 503 that explains the basket is retained. Identical checkout requests use a stable idempotency key. Product IDs are included in Stripe product metadata; paid order names, prices and quantities come from expanded paid line items, with totals checked before persistence. Order creation and consumption of paid basket quantities share a transaction, preserving quantities added during payment. Duplicate sessions/events do not create duplicate orders or duplicate provider notifications. Completed and delayed-success events and authorized client confirmation share the same fulfillment service.  
**Verification:** Genuine Stripe test-mode creation and retry passed through the application endpoint; the session was expired without payment. Isolated signed-webhook tests passed for paid fulfillment, later catalogue/basket changes, unpaid/forged/other-client rejection, retries, basket recovery, Provider status transitions and notifications. External webhook delivery and a real paid purchase remain untested.

**Category:** Bug  
**Severity:** High  
**Role:** Client  
**Page / Location:** `/cart/{providerId}` — Checkout  
**Issue:** A valid basket cannot proceed through checkout in either the newly created QA store or the existing Demo Restaurant.

**Steps to Reproduce:**

1. Register/sign in as a Client.
2. Add QA Harvest Bowl from QA October Bistro; increase quantity to two.
3. Open its basket and verify the $25.00 subtotal.
4. Click Checkout.
5. Check Orders and repeat once.
6. Separately add Tiramisu from Demo Restaurant and click Checkout in its $6.50 basket.

**Expected Behavior:** Checkout advances to the intended payment/order step, with clear feedback.  
**Actual Behavior:** All three attempts returned HTTP 500 from `/api/v1/client/{providerId}/payments`. The UI showed “An unexpected error occurred. Please try again later.” Baskets remained populated; the tested Client's Orders page remained empty.  
**Why It Matters:** The principal conversion flow is blocked for both tested stores. Generic feedback gives the customer no actionable recovery path.  
**Suggested Improvement:** Investigate and restore the checkout integration; provide payment-specific recovery feedback and verify the complete order lifecycle afterward. Preserve baskets and protect retries from duplicate payment/order creation.  
**Evidence:** [Checkout screenshot](<C:/Backend project/.qa-review/checkout-failure.png>). Store IDs tested: QA `0f0b3784-7f90-4b5e-a348-4c3899c27d51`; Demo Restaurant `36a96fff-f247-4b5e-b6d3-6fc2436092db`.

### QA-002 — [Solved] Catalogue-read-only staff can modify store identity

**ID:** QA-002  
**Status:** **Solved** — confirmed finding (fixed 3 October 2026; verified 4 October 2026)  
**Resolution:** Verified the existing ProviderStore.Update fix: store readers have disabled identity fields, no upload/Save controls, and guarded mutation methods. Store routes and backend write/image endpoints also have explicit store permissions. Frontend regressions and direct API permission tests passed: catalogue-read-only users cannot access Store endpoints, Store.Read users can view but cannot mutate identity/images, and authorized editors can persist changes. This is targeted authorization coverage, not a complete security audit.

**Category:** Security/Permission Issue  
**Severity:** High  
**Role:** Provider staff  
**Page / Location:** `/provider/store`  
**Issue:** Staff granted only category-read and product-read permissions can edit and save store-level information.

**Steps to Reproduce:**

1. As Provider owner, create a role with only `ProviderCategory.Read` and `ProviderProduct.Read`.
2. Create staff assigned to that role and sign in as the staff account.
3. Open Store; change Company to “QA October Bistro Staff Probe.”
4. Save and reload Store.

**Expected Behavior:** A role configured with only read permissions cannot persist unrelated store changes, unless universal staff store-edit access is an explicit product policy clearly disclosed to the owner.  
**Actual Behavior:** Company and phone fields, image upload and Save were enabled. The company-name change saved and survived reload. Other product write controls were correctly hidden for this same role.  
**Why It Matters:** Owners cannot infer the effective write scope from the selected permissions. Store identity is visible to customers.  
**Suggested Improvement:** Define an explicit store-edit permission or owner-only rule and enforce the intended scope consistently. If every staff member is intentionally allowed to edit Store, disclose that exception when assigning roles.  
**Evidence:** [Persisted staff change](<C:/Backend project/.qa-review/readonly-staff-store-update.png>). The fictional store name was restored after the test. Phone/image mutation by this staff account was not tested; those controls were observed enabled.
